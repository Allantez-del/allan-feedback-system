# DynamoDB Design

## Table Configuration

The Allan Feedback System stores feedback in the DynamoDB table `allan-feedback`.

| Setting | Implemented value |
| --- | --- |
| Billing mode | `PAY_PER_REQUEST` |
| Partition key | `feedbackId` |
| Partition key type | String (`S`) |
| Point-in-Time Recovery | Enabled |

The table uses DynamoDB on-demand capacity. This allows the table to scale with request volume without provisioning or manually adjusting capacity units. It is a practical choice for the demonstration because traffic may be irregular and the system remains small. The trade-off is that on-demand pricing is based on request usage and can cost more than provisioned capacity when access patterns become consistently high and predictable.

## Item Design

Each feedback submission is stored as one DynamoDB item. The implemented fields are:

- `feedbackId` - generated by AWS Lambda as a UUID and used as the partition key.
- `customerName` - optional customer name.
- `email` - optional customer email address.
- `rating` - required integer from 1 to 5.
- `category` - required supported feedback category.
- `message` - required feedback message.
- `submittedAt` - UTC timestamp generated by Lambda when the feedback is submitted.

Lambda validates the request before writing the item. Optional fields are stored only when supplied with non-empty values.

## Access Pattern

Customers and staff do not receive direct DynamoDB permissions. All database access is performed by the Lambda function through the API:

- `POST /feedback` validates the request and uses DynamoDB `PutItem` to persist the feedback.
- Authorized `GET /feedback` requests use DynamoDB `Scan` to retrieve feedback records.
- Retrieval is limited to 20 items and the returned records are sorted by `submittedAt`, newest first.

## Current Use of Scan

`Scan` is acceptable for the current demonstration because the dataset and expected traffic are small, and it keeps the data model simple. It allows the implementation to retrieve the current set of feedback records without introducing an additional index or query-specific key design.

`Scan` is not ideal for a production workload because it examines table items rather than directly targeting the records needed by a request. As the table grows, scans can consume more read capacity, increase latency, and return incomplete application-level pages unless pagination is handled explicitly.

## Future Improvements

A production-oriented design should use a query-based access pattern. Possible improvements include:

- Introduce a suitable sort-key or secondary-index design for staff retrieval, such as an index organized by submission time.
- Replace `Scan` with DynamoDB `Query` against the table or an appropriate global secondary index.
- Add pagination using DynamoDB `LastEvaluatedKey` and a client-facing continuation token.
- Define access patterns first so indexes support the required filters and ordering without reading unrelated items.

These changes are future improvements; the current implementation intentionally remains a small demonstration system.
